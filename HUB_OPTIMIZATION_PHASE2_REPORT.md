# Gina-Hub Performance Optimization — Phase 2 Report

Branch: `gina-hub-main`. Continues directly from Phase 1 (`HUB_OPTIMIZATION_PHASE1_REPORT.md`), which established
the single-void-world Hub-Map architecture. This phase covers: complete removal of Gina-owned bStats, JAR-size
audit, a real protocol-level load-test harness, the actual player-ramp bottleneck (a measured O(n²) issue), a
`server.properties` hosting-panel compatibility fix, startup profiling, JVM memory-configuration findings, and
leak/soak testing.

## 1. Test environment

All measurements in this report, unless explicitly marked "production observation," were taken on:

- **CPU**: AMD Ryzen 9 7945HX, 16 cores / 32 logical threads
- **RAM**: 33,487,876,096 bytes (~31.2 GiB)
- **OS**: Windows 11 Home, build 10.0.26200
- **Java**: Temurin 21.0.11+10 (JDK 21)
- **JVM args**: stated per-measurement (this phase tests multiple configurations explicitly, see §8)

This is a large, uncontended dev workstation, not a representative 2-4 vCPU production Hub VM — CPU-percentage
figures and thread-parallelism-derived numbers (e.g. G1 thread counts) are not directly portable to production
without re-measurement there, and are labeled as such throughout.

**Production observations** (reported by the maintainer from a separate Linux/Pterodactyl deployment of the jar
delivered after Phase 1, not independently reproduced by this environment): warm startup ≈6.854s, Hub-Map
world-prep ≈0.143s, idle container memory ≈1.01 GiB/2 GiB with one player, launch command
`java -Xms128M -XX:MaxRAMPercentage=95.0 -Dterminal.jline=false -Dterminal.ansi=true -jar server.jar`. These are
used to prioritize this phase's work but are not re-verified line-for-line on Windows; where this environment
tests an analogous configuration, that is stated explicitly rather than conflated with the Linux numbers.

## 2. Load-test harness

`benchmark/loadbot/GinaLoadBot.java` — a from-scratch Minecraft protocol client, not a wrapper around any public
library (none exists for this fork's protocol version). Built by reading this fork's own decompiled packet
definitions (`paper-server/src/minecraft/java/net/minecraft/network/protocol/`) rather than guessing at a public
spec.

**Implemented and verified real (not simulated) protocol behavior:**
- Full handshake → login → configuration → play state machine, including mid-login compression negotiation
- Continuous walk-speed movement (~4 blocks/s, heading changes) that drifts across chunk boundaries realistically
- Keep-alive echo (configuration and play state)
- Teleport acknowledgement (parses the teleport ID from `ClientboundPlayerPositionPacket`, replies correctly)
- Real chunk packet receipt (counted, not parsed — proves the server did the real serialization work without the
  bot spending CPU decoding NBT it doesn't need)

**Known limitation, by design, documented rather than silently worked around:** chat/command stimulus is
disabled. `ServerboundChatCommandPacket`'s signed-message wire format (signature tracking, last-seen-message
acknowledgements) is nontrivial; an incorrect first attempt at encoding it was found to corrupt server-side
packet decoding for the *following* packet, dropping the connection — the actual bug, and the debugging process
that found it (checking exact bytes sent, not guessing), is preserved in the harness's git history for future
reference. Movement, keep-alive, teleport-ack, and chunk receipt are real and protocol-correct; chat/commands are
not simulated in Phase 2.

**Debugging notes preserved as harness-quality evidence, not just a working artifact:** three distinct real
protocol bugs were found and fixed while getting this harness to work — a login-phase compression bug (packets
after mid-login compression negotiation were read via the wrong, non-compression-aware path), the chat-command
corruption above, and a movement-clamp bug (bots walking off the edge of the actual 101×101 benchmark platform
into the void, from a leftover 500-block-border assumption). All three are fixed; see `benchmark/README.md`.

## 3. Benchmark fixture

`benchmark/scripts/setup-benchmark-world.sh` deterministically builds, against a clean Hub-Map:

- 101×101 `smooth_stone` platform at y=64 (bedrock underneath at y=63), replacing the single-bedrock clean-install

- 6 static NPC-proxy `armor_stand` entities (`NoAI`, `Invulnerable`, `Silent`) in a ring around spawn
- 4 `text_display` hologram entities
- 8 decorative `item_display` entities

18 non-player entities total, deterministic, saved as a reusable world fixture (`benchmark/hub-map-fixture/`, not

Hub's actual content or entity count (see Phase 1 §"Do not optimize the empty server only," carried forward).

## 4. bStats removal (recap, unchanged from prior checkpoint)

`com.destroystokyo.paper.Metrics` — Paper's own embedded bStats client (already customized in the earlier rebrand
to report under a "Gina-Hub" identity) — was deleted along with its startup call site. Verified: zero-plugin clean
boot creates no `bStats` directory/config; the built jar contains zero `Metrics`/`bstats` classes; the
`org.bstats` API itself is untouched, so third-party plugins (LuckPerms) still bundle and run their own
independently.

## 5. Runtime bottleneck #1 — locator-bar waypoint tracking (O(n²))

### Root cause

`ServerWaypointManager` (`net.minecraft.server.waypoints`) maintains a `Table<ServerPlayer, WaypointTransmitter,
Connection>` (Guava `HashBasedTable`) representing every player's locator-bar connection to every waypoint
transmitter. Since every player is itself a waypoint transmitter by default (`LivingEntity.isTransmittingWaypoint()`
checks a base attribute that's positive for players regardless of any gamerule), `addPlayer()`/`updatePlayer()`/
`updateWaypoint()` all iterate the full player set on every join and every per-player update — effectively
all-players-to-all-players work, gated only by the `GameRules.LOCATOR_BAR` gamerule (which defaulted to `true`
and was never touched by Phase 1's gamerule audit).

### Fix

Flipped `LOCATOR_BAR`'s default to `false` — same pattern as Phase 1's other simulation gamerules (`advance_time`,
`advance_weather`, `random_tick_speed`, `spawn_mobs`). Zero new patch machinery, fully admin-reversible via
`/gamerule locator_bar true`, zero effect on the `org.bstats`-style "third party can still use the underlying
system" boundary since this is vanilla gamerule infrastructure, not something Gina invented.

### Measurement (before/after, 150-player join burst, 2GB heap, identical benchmark world/JVM/bot pattern)

A first "after" attempt was **invalid** and discarded: it reused a world save whose `level.dat` had `locator_bar`
persisted as `true` from before the code change (gamerules are per-world persisted state; a code-level default
only applies to brand-new worlds). Caught by checking `/gamerule locator_bar` before trusting the result;
corrected by explicitly resetting the fixture's gamerule and re-verifying `false` before re-measuring.

| | Before | After |
|---|---|---|
| TPS (10s window) | 15.51 | 20.0 |
| Max tick duration | 1369–1455ms | 27–64ms |
| CPU (process, 1m) | 14–15% | 0–2% |
| Heap used | 65–73% of 2GB | 28% of 2GB |

Allocation profile (`jdk.ObjectAllocationSample`): Guava `Table` churn (`StandardTable$Row`/`Row$2`/
`EntrySetIterator$1EntryImpl`, ~1700 combined samples) disappeared entirely from the post-fix top-15; waypoint
object/packet allocations (`TrackedWaypoint$Vec3iWaypoint`, `ClientboundTrackedWaypointPacket`) dropped from 716
to 33 samples (>95% reduction).

### Re-verified at original (1GB heap) conditions, matching the primary ramp exactly

| Players | Metric | Before | After |
|---|---|---|---|
| 150 | TPS (10s) | 16.14 | *20.0 / 19.9 (1m) |
| 150 | Median MSPT | 7.4–8.0ms | 4.8–6.6ms |
| 150 | p95 MSPT | 25.2–26.6ms | 6.6–13.4ms |
| 150 | Max tick | 1369.5ms | 403.9ms |
| 150 | CPU (process) | 19–24% (1m) | 2–8% |
| 150 | Heap used | 73% | 55% |
| 200 | TPS (10s) | **8.58 (UNHEALTHY)** | **19.97–19.99 (EXCELLENT)** |
| 200 | Bots logged in | **177/200 (23 stuck)** | **200/200** |
| 200 | Max tick | 2869.7ms | 382.7ms |
| 200 | CPU (process) | ~15% | 3–7% |
| 200 | Heap used | 89% | 75% |

N=200 moved from a genuinely broken state (TPS 8.58, a quarter of connecting bots stuck mid-login) to healthy.
This confirms locator-bar tracking was the dominant cause of the degradation seen across the entire original
150–200 range, not primarily heap pressure — corroborated independently by the GC log showing repeated
"Evacuation Failure" and Full GC compactions at the 1GB/150-player *before* point, which did **not** recur after
the fix, and by a 2GB-heap isolation test that still showed the ~1.4s stall pre-fix despite having 3x the heap
headroom (22% Old Gen utilization) — ruling out heap-cap-as-primary-cause before the real fix was found.

### Compatibility retest

LuckPerms (enables, 718–725ms, no errors), self-authored Bukkit/Paper-API test plugin, 3–5 bot smoke connections,
block modification, entity spawning, time/weather commands, and `/gamerule` queries — all retested clean after
the change.

## 6. Runtime bottlenecks #2 and #3 — not found at comparable scale

Fresh profiling at N=200 on the post-fix build (both with and without LuckPerms present, to isolate plugin noise
from core Gina-Hub behavior) found **no second bottleneck of anywhere near locator-bar's magnitude**. The new
top-of-stack CPU hotspot (`Reference2IntOpenHashMap.find`/`shiftKeys`, ~10% of samples) traces to
`ca.spottedleaf.moonrise.common.misc.NearbyPlayers.tickPlayer()` — Moonrise's own player-proximity-tracking
machinery, which is core, required, already-optimized engine infrastructure with inherently per-player cost, not
Hub-specific waste. Remaining hotspots (Netty packet I/O, `TicketSet.expireAndRemoveInto` chunk-ticket churn,
`PalettedContainer.reencodeContents` chunk re-encoding) are likewise core and roughly proportional to player
count.

One residual, genuinely Hub-attributable item was found and deliberately **not** patched: `ServerWaypointManager`'s
*outer* per-player iteration (`Sets.difference`, `ImmutableSet.copyOf`) still runs for every player even with
`locator_bar=false` — only the inner connection-creation is gated. This measured at ~3% of samples (9/~300).
Short-circuiting the outer loop would require either a broader assumption (no per-world/per-player locator-bar
overrides ever matter) or additional state tracking to detect "nobody has it enabled," and the expensive part
(connection object creation, the actual O(n²) driver) is already eliminated. Per this phase's own stop condition
("if an optimization provides negligible measurable benefit... REVERT IT"), this was examined and consciously
left alone rather than forced into a report metric.

**Given this, effort was redirected to startup and memory — both large, unaddressed, real costs with materially
more addressable headroom than chasing single-digit-percent noise in player-scaling profiles.**

## 7. Startup — JFR findings

Startup JFR (`-XX:StartFlightRecording=settings=profile`, warm restart) confirms Phase 1's timestamp-based
finding with actual sampled evidence rather than assuming from timestamps alone: searching the full call stack
(not just the leaf frame) of every `jdk.ExecutionSample` during boot, **"Codec" appears in 119 of 125 samples
(95%)**, with heavy "Tag" (204 stack-frame matches) and "Registry" (32) presence too. The dominant startup cost
is Mojang's Codec-based JSON/NBT deserialization for registries, tags, recipes, and worldgen data — this is
foundational, required Minecraft data-loading (it defines what blocks/items/biomes/recipes exist as data-driven
objects), not an incidental inefficiency.

`PalettedContainer.reencodeContents` also appeared prominently during boot (18/125 samples, ~14%) from persistent
chunk loading/light-engine setup — this is real chunk-loading work, required to open an existing world.

### Classification

| Subsystem | Classification | Reasoning |
|---|---|---|
| Registry/tag Codec parsing | **REQUIRED** | Defines the data-driven game model; no safe bypass found |
| Recipe loading (`Loaded 1470 recipes`) | **REQUIRED / NOT WORTH TOUCHING** | ~1.6s of the ~9.5s total (Phase 1 measurement); Bukkit/Paper APIs expose recipes and plugins may query them at any time post-boot — deferring risks a plugin querying recipes during its own `onEnable()` before lazy-loading finishes. Modest saving, real compatibility risk: kept. |
| Advancement loading (`Loaded 1584 advancements`) | **NOT WORTH TOUCHING** | Same category as recipes; not separately measured as a distinct large cost this phase. |
| DataConverter init | **REQUIRED** | Data-safety-critical (legacy world upgrade path); ~300–400ms is a small fraction of total startup and skipping it risks silent data corruption for anyone loading an older-format world. |
| Chunk loading/light engine (`PalettedContainer.reencodeContents`) | **REQUIRED** | Necessary to open the existing Hub-Map world; already fast in absolute terms (Hub-Map prep itself is ~0.2–0.9s in this environment, ~0.143s per the Linux production observation). |
| Spark background profiler auto-start | **CAN BE CONDITIONALLY BYPASSED (deferred, not implemented this phase)** | See §9 — not removed, per explicit instruction to keep profiling capability during this phase. |

No safe, low-risk startup change was identified this phase beyond what Phase 1 already delivered (the Hub-Map
world-prep reduction from 3.40s to ~0.2–0.9s). Warm startup in this environment remains ≈9.5–9.8s across all
builds tested this phase (locator-bar fix and server.properties fix are both startup-neutral, confirmed by
direct comparison). The Linux production observation of ≈6.854s is meaningfully faster than this Windows
environment's ≈9.5–9.8s for reasons not isolated this phase (likely OS/filesystem/JIT-warmup differences, not
something this environment can attribute further without Linux access) — the <5s / <3–4s targets are not met in
this environment and were not forced via a risky change given the "do not compromise correctness to hit a
number" instruction.

## 8. JVM memory configuration

Phase 1's NMT profiling used `-Xms1G -Xmx1G` and found ~800MB of the 1024MB heap was committed-but-idle,
hypothesizing that `Xms == Xmx` was forcing G1 to commit the full heap upfront regardless of actual need. This
phase validates that hypothesis directly, using a configuration analogous to the reported Pterodactyl launch
command (`-Xms128M -XX:MaxRAMPercentage=95.0`) — tested here as an explicit `-Xms128M -Xmx1024M` since this
environment has no container/cgroup memory ceiling for `MaxRAMPercentage` to compute against, and that difference
is stated explicitly rather than silently assumed equivalent.

### Idle, `-Xms128M -Xmx1024M` vs. Phase 1's `-Xms1G -Xmx1G`

| | Phase 1 (`Xms=Xmx=1G`) | Phase 2 (`Xms128M Xmx1024M`) |
|---|---|---|
| Heap committed | 1024 MB (forced full) | 544 MB (grew on demand) |
| Live heap used | ~221–235 MB | ~224–229 MB (same workload, as expected) |
| Process RSS | ~1.38–1.44 GB | **878 MB (~35–38% reduction)** |
| Total NMT committed | 1370 MB | 893 MB |

### Under real load (100 players, same low-`Xms` config)

TPS held 19.99–20.0, median MSPT 0.8–2.8ms, p95 1.2–10.5ms, max tick 19.8–42.5ms — **no latency penalty observed
from starting the heap small and letting it grow under load.** Heap committed grew from 544MB (idle) to 629MB
(100 players); RSS grew from 878MB (idle) to ~1.03GB (100 players), roughly **1.5MB RSS added per player** —
consistent with, though not identical in absolute terms to, the earlier per-player memory-scaling question from
Phase 1.

### 1 GB Hub target — tested, not assumed

The fixed non-heap JVM/Paper overhead (Metaspace ~140–150MB, Class space ~24MB, GC bookkeeping ~104MB, Code
cache, Symbol table, thread stacks, NMT's own tracking overhead) totals **~650–700MB regardless of heap sizing**
— this doesn't shrink with a lower `Xmx`. With `-Xmx1024M`, idle RSS alone is already 878MB before any player
connects. **A genuine 1 GB *container* (not just a 1GB heap number) is therefore not comfortably sufficient for
this workload once real non-heap overhead is accounted for** — there is well under 350MB of true headroom for
heap growth once the fixed overhead is subtracted from a 1GB ceiling, which is tight even for the ~100–150 player
range this phase measured needing ~400MB of live heap. This is reported honestly rather than assumed: **the
safe minimum for the tested load range (up to 200 players, benchmark-fixture content) is closer to 1.5–2GB total
container memory**, not 1GB. This does not account for the eventual real Hub plugin's additional overhead (see
Phase 1 §"Account for future Hub plugin," unchanged conclusion: leave headroom).

No GC-thread-count changes or other GC tuning were made this phase — Phase 1's finding that this dev machine's
32-core auto-scaled G1 thread count is not representative of production remains unvalidated on a smaller-core
target and was not acted on blindly, per the explicit "do not tune GC blindly" instruction.

## 9. `server.properties` migration fix

### Symptom (reported production observation)

Every restart logged: `Gina-Hub migration: server.properties already exists at its new location; archived the
old copy...` — accumulating a new backup file in `configs/legacy-backup/` on every boot.

### Root cause

Phase 1's rebrand had moved `server.properties` to `configs/server.properties` (the `-c`/`--config` CLI default
in `CraftBukkit`'s `Main.java`). Hosting panels — Pterodactyl eggs specifically — write `server.properties`
directly at the conventional root path on every (re)start regardless of Gina's own layout, since that's the one
location every panel's "server.properties parser" feature already knows how to find. With the canonical read
location at `configs/`, every restart found a freshly panel-written root copy *and* the already-migrated
`configs/` copy simultaneously, and the migration logic (correctly, by its own design) archived the "duplicate" —
except the duplicate reappeared every single boot, since the panel had no way to know not to write it.

### Fix

Reverted `server.properties` to the conventional root location — the exact same rationale and pattern already
established for `eula.txt` in the prior rebrand (a code comment already documented this precedent: *"the one file
every hosting panel, Pterodactyl egg, and custom startup script already knows how to find and write"*). Only
`server.properties` moved; `bukkit.yml`, `commands.yml`, `spigot.yml`, `help.yml`, `permissions.yml`, and
`gina-config.yml` remain under `configs/` unchanged. Added `migrateServerPropertiesBackToRoot()`, mirroring the
existing `migrateEulaBackToRoot()`, to pull back an existing `configs/server.properties` from an earlier
Gina-Hub build exactly once, preserving custom values.

### Verified with three scenarios

1. **Clean install**: `server.properties` lands at root; nothing in `configs/`.
2. **Upgrade from old layout**: a `configs/server.properties` with a custom value (`motd=OLD CUSTOM MOTD FROM
   CONFIGS`) is moved to root, value intact, logged once.
3. **The actual reported collision**: a stale `configs/server.properties` alongside a panel-rewritten root copy
   (`motd=PANEL WROTE THIS AT ROOT`) — the panel's root value is left completely untouched, the stale `configs/`
   copy is archived exactly once (`configs/legacy-backup/server.properties.<timestamp>.old`), and **a second
   restart afterward produces zero migration log lines and zero new backup files** — full idempotency confirmed.

## 10. Memory leak test

Methodology: 4 cycles of connect 100 bots → stabilize → full disconnect (bots run for a fixed duration then all
close) → wait 5s → force `GC.run` → measure post-GC heap, against a single long-lived server process (no restart
between cycles), `-Xms128M -Xmx1024M`.

| Cycle | Post-GC live heap | RSS |
|---|---|---|
| 1 | 263.8 MB | 1035.5 MB |
| 2 | 266.7 MB | 1039.8 MB |
| 3 | 265.7 MB | 1080.2 MB |
| 4 | 265.8 MB | 1095.2 MB |

**Live heap: flat across all 4 cycles (±1%), no leak trend.** Metaspace grew a negligible ~1.5MB total across 4
cycles (148.3→149.8MB), consistent with normal one-time JIT/`invokedynamic` call-site resolution rather than a
leak — it plateaus rather than growing per-cycle. RSS showed modest growth (~5.5% over 400 total connect/
disconnect events across 4 cycles), most plausibly attributable to the same metaspace/code-cache settling rather
than retained per-player objects, since live heap itself did not move. No evidence of a per-player state leak
(players, connections, chunks, waypoint state, scoreboard state, scheduler tasks) in the locator-bar-fixed build.

## 11. Soak test

**Duration: 8 minutes (480s), 100 concurrent bots, `-Xms128M -Xmx1024M`, single continuous run (not multiple
short cycles).**

- All 100 connections remained stable for the full duration — 0 failures, 0 drops.
- TPS: 19.97–20.0 throughout, including the 5-minute and 15-minute rolling windows both reading 20.0 at the end.
- Tick durations: median 0.7–2.7ms, p95 1.2–10.1ms, max 18.9–20.2ms — no growing tail latency over the run.
- Final post-GC live heap: 262.4 MB — statistically identical to the leak test's baseline (~264–266MB across its
  4 cycles), confirming no drift over a materially longer continuous run.
- Final RSS: 1.116 GB — flat versus the mid-soak sample (~100s in: 1.124 GB) and the leak-cycle test's final
  state (~1.10–1.12 GB); no runaway growth over 8 minutes.
- Thread count: 88, stable.

## 12. Compatibility (final regression pass)

Retested against the fully-optimized build (locator-bar fix + server.properties fix): LuckPerms (enables
cleanly, 718–725ms, `/lp info` reports correctly including the "Gina-Hub" server brand), block modification
(`/setblock`), entity spawning (`/summon armor_stand`), time/weather commands, `/gamerule` queries (confirmed
`locator_bar` and `advance_time` both read `false` as expected), and repeated bot connections (3–5 bots,
clean login/movement/disconnect). No regressions found.

## 13. Capacity

**Tested populations this phase: 10, 25, 50, 100, 150, 200** (both before and after the locator-bar fix, at
1GB heap; 150 and 200 additionally at 2GB heap for isolation).

| Players | Status (post-fix, 1GB heap) |
|---|---|
| 10–100 | EXCELLENT — TPS 20.0, sub-3ms median MSPT throughout the original ramp |
| 150 | HEALTHY — TPS ~20 (was DEGRADED pre-fix: TPS 16.14, 1.4s stalls) |
| 200 | HEALTHY/EXCELLENT — TPS 19.97–19.99, all 200 bots connect (was UNHEALTHY pre-fix: TPS 8.58, 23/200 bots stuck) |

**Not tested this phase**: 250+. Given 200 is now healthy with meaningful CPU/heap headroom remaining (75% heap,
3–7% process CPU on this 32-thread dev machine), pushing further is a reasonable Phase 3 candidate, but this
phase's time was allocated to startup/memory/migration fixes per the explicit priority order given. **Comfortable
capacity vs. stress limit is therefore reported as: comfortably healthy through 200 players (measured); beyond
200 is unmeasured, not "unsupported."**

**1 GB container**: not comfortably sufficient for this workload once real non-heap JVM overhead (~650–700MB
fixed) is accounted for — see §8. A 1.5–2GB container is the realistic safe minimum for the tested range.

This benchmark uses the fixture described in §3 (18 static entities, no plugins beyond the harness's own
bookkeeping plugin) — these are **CORE GINA-HUB** numbers, not a claim about the eventual real Hub's capacity once
the actual Gina Hub plugin (NPCs, holograms, cosmetics, UI, tab, scoreboard, chat, parties, network integration)
is running. That plugin will add its own CPU/memory/allocation cost on top of everything measured here.

## 14. Remaining bottlenecks (ranked by measured impact)

1. **Startup registry/tag/recipe Codec parsing** (~65% of warm startup per Phase 1 timestamps, confirmed via JFR
   as Codec-dominated) — REQUIRED, no safe reduction found this phase.
2. **Fixed non-heap JVM/Paper overhead** (~650–700MB: metaspace, class space, GC structures, code cache, symbol
   table) — largely fixed regardless of tuning; the metaspace component (28–32k loaded classes) is the largest
   single piece and was not reduced this phase (see Phase 3 recommendations).
3. **Residual `ServerWaypointManager` outer-loop iteration** — ~3% of samples at 200 players, examined and
   consciously left unpatched (see §6).
4. **Windows-vs-Linux startup gap** (~9.5–9.8s here vs. ≈6.854s reported in production) — not isolated this
   phase; likely OS/filesystem/JIT-warmup related, needs Linux-side profiling this environment cannot perform.
5. **Chat/command stimulus unimplemented in the load harness** — a testing-capability gap, not a Gina-Hub runtime
   issue; documented in `benchmark/README.md`.

## 15. Phase 3 recommendations (not implemented)

- Build (or port) a working Linux JFR/NMT profiling pass to close the Windows/Linux startup and memory gaps this
  phase could not directly attribute.
- Investigate metaspace/loaded-class reduction (lazy class initialization for subsystems Gina-Hub never touches,
  e.g. survival-only crafting UI classes) — "don't load it," not "delete it from the JAR," per this phase's own
  standing rule.
- Extend the player ramp past 200 (250, 300, 400+) now that 200 is healthy with headroom.
- Re-run the full ramp with the eventual real Gina Hub plugin installed, to get REPRESENTATIVE (not just CORE)
  capacity numbers, per Phase 1's "do not optimize the empty server only" principle.
- Implement the load harness's chat/command packet support properly (read the real signed-message wire format
  from source) so join-storm and chat-load testing can be added.
- Re-validate G1 thread-count / GC tuning on a machine matching the actual target Hub VM spec, not this 32-core
  dev box.
- If a future profiling pass at higher player counts (250+) reveals a new O(n²)-shaped pattern, apply the exact
  same measure→attribute→fix→re-measure discipline used for the locator-bar fix in this phase.
